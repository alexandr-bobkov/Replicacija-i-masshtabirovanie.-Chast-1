## ЧАСТЬ 1: Теория и готовые ответы на задания

### Задание 1: Различия режимов репликации master-slave и master-master

**Репликация** — это механизм копирования данных с одного сервера базы данных на другие в режиме реального времени. Это необходимо для защиты от потери информации (бэкап) и распределения пользовательской нагрузки.

#### 1. Режим master-slave (Главный — Подчинённый)
В этой схеме между серверами установлено чёткое, жесткое разделение обязанностей:
* **Принцип работы:** Есть один главный сервер (master) и один или несколько подчиненных (slave).
* **Потоки данных:** Все операции по изменению данных (`INSERT` — добавление, `UPDATE` — изменение, `DELETE` — удаление) приложение отправляет строго на master-сервер. Master делает записи у себя и заносит их в специальный файл бинарного лога (Binary Log). Slave-серверы постоянно читают этот файл по сети и повторяют все действия у себя.
* **Режим доступа:** Master открыт для чтения и для записи. Все slave-серверы принудительно переводятся в безопасный режим `read_only` (только для чтения), чтобы пользователи не рассинхронизировали базу.
* **Назначение:** Применяется на большинстве сайтов в интернете. Клиенты просматривают товары (нагружают чтением Slave), а оформляют заказы (нагружают записью Master).
* **Отказоустойчивость:** Если ломается slave, система работает дальше. Если падает master, сайт временно перестает принимать новые записи, пока администратор вручную не сделает один из слейвов новым главным сервером.

#### 2. Режим master-master (Главный — Главный)
В этой архитектуре все сервера в сети обладают абсолютно равными правами:
* **Принцип работы:** Оба сервера одновременно выступают и в роли главного, и в роли подчиненного по отношению друг к другу. Логи изменений передаются перекрестно в обоих направлениях.
* **Потоки данных:** Пользовательское приложение может записывать новые данные на любой из серверов. Изменения, сделанные на первом сервере, автоматически прилетят на второй, и наоборот.
* **Режим доступа:** Все сервера полноценно работают в режиме чтения и записи.
* **Назначение:** Применяется в очень крупных, географически распределенных системах, где требуется максимальная отказоустойчивость на запись (High Availability).
* **Отказоустойчивость и риски:** Если один сервер полностью сгорит, сайт мгновенно переключится на запись во второй без пауз в работе. Однако этот режим требует тонкой настройки генерации идентификаторов (чтобы ключи строк не пересекались) и несет в себе высокий риск **конфликтов репликации**, если одну и ту же строчку изменят одновременно на двух серверах.

## ЧАСТЬ 2: Исходный код конфигурационных файлов

Просто скопируйте текст под каждым заголовком и сохраните в соответствующий файл в вашей папке проекта. Пароль администратора (`root`) для всех серверов жестко задан как `password123`.

### 📄 Файл 1: `master.cnf`
*Этот файл содержит системные настройки главного сервера. Docker автоматически подложит его в настройки MySQL.*
```ini
[mysqld]
# server-id — это уникальное число сервера в сети репликации. У Мастера всегда ставится 1.
server-id = 1

# log-bin включает ведение бинарного лога (Binary Log) и задает базовое имя для его файлов.
log-bin = mysql-bin

# binlog_do_db указывает серверу записывать в лог изменения только для учебной базы sakila.
binlog_do_db = sakila
```

### 📄 Файл 2: `slave.cnf`
*Этот файл содержит системные настройки подчиненного сервера.*
```ini
[mysqld]
# Уникальный номер реплики. Он ОБЯЗАН отличаться от ID мастера, поэтому ставим 2.
server-id = 2

# relay-log включает ведение ретрансляционного лога (Relay Log) для приема данных от Мастера.
relay-log = mysql-relay-bin

# read_only = 1 переводит Слейв в режим "Только для чтения", защищая базу от локального рассинхрона.
read_only = 1
```

### 📄 Файл 3: `init/master-init.sql`
*Скрипт автозапуска для Мастера. В СУБД MySQL 8.0/8.4 команды создания пользователя и выдачи прав нельзя выполнять одной строкой как единый скрипт — база их сбросит. Но при автоинициализации Docker выполняет их пошагово из файла безупречно.*
```sql
-- 1. Стираем старый профиль, если он остался в памяти
DROP USER IF EXISTS 'repl_user'@'%';

-- 2. Создаем технического пользователя со старым совместимым шифрованием пароля (mysql_native_password).
-- Это критически важно, так как новые версии MySQL используют caching_sha2, который слейв без SSL не примет!
CREATE USER 'repl_user'@'%' IDENTIFIED WITH mysql_native_password BY 'my_secure_repl_password_123';

-- 3. Выдаем пользователю права на чтение бинарных логов репликации
GRANT REPLICATION SLAVE ON *.* TO 'repl_user'@'%';

-- 4. Принудительно сохраняем права в системную память сервера
FLUSH PRIVILEGES;
```

### 📄 Файл 4: `init/slave-init.sql`
*Скрипт автозапуска для Слейва. При самом первом «чистом» старте контейнеров имя файла лога Мастера ВСЕГДА называется `mysql-bin.000001`, а стартовая позиция ВСЕГДА равна `157`. Мы используем этот стандарт для полной автоматизации связки.*
```sql
-- 1. Связываем Слейв с Мастером по фиксированным стартовым координатам.
-- В MASTER_HOST мы пишем имя сервиса 'mysql-master' — Docker внутри сети сам сопоставит его с IP-адресом.
CHANGE MASTER TO
  MASTER_HOST='mysql-master',
  MASTER_USER='repl_user',
  MASTER_PASSWORD='my_secure_repl_password_123',
  MASTER_LOG_FILE='mysql-bin.000001',
  MASTER_LOG_POS=157;

-- 2. Включаем фоновые потоки репликации
START SLAVE;
```

### 📄 Файл 5: `docker-compose.yml`
*Главный сценарий оркестрации. Мы прокидываем наши SQL-скрипты в специальную системную папку контейнеров `/docker-entrypoint-initdb.d/`. Всё, что лежит в этой папке, Docker автоматически запускает при первом включении баз.*
```yaml
version: '3.8'

networks:
  replication_net:
    driver: bridge # Создаем изолированную сеть, чтобы контейнеры общались по своим именам

services:
  mysql-master:
    image: mysql:8.0 # Официальный стабильный образ MySQL 8.0
    container_name: mysql-master
    # command принудительно разрешает внешнюю авторизацию клиентов без SSL
    command: --default-authentication-plugin=mysql_native_password
    environment:
      MYSQL_ROOT_PASSWORD: password123 # Явно прописываем root-пароль администратора
    ports:
      - "3306:3306" # Проброс портов: Мастер будет доступен на порту 3306 вашего компьютера
    volumes:
      - ./master.cnf:/etc/mysql/conf.d/master.cnf
      # Монтируем скрипт инициализации в системную папку автозапуска Docker Мастера:
      - ./init/master-init.sql:/docker-entrypoint-initdb.d/master-init.sql
    networks:
      - replication_net

  mysql-slave:
    image: mysql:8.0
    container_name: mysql-slave
    command: --default-authentication-plugin=mysql_native_password
    environment:
      MYSQL_ROOT_PASSWORD: password123
    ports:
      - "3307:3306" # Проброс портов: Слейв будет доступен на порту 3307 вашего компьютера
    volumes:
      - ./slave.cnf:/etc/mysql/conf.d/slave.cnf
      # Монтируем скрипт инициализации в системную папку автозапуска Docker Слейва:
      - ./init/slave-init.sql:/docker-entrypoint-initdb.d/slave-init.sql
    depends_on:
      - mysql-master # Слейв начнет запуск только ПОСЛЕ того, как поднимется Мастер
    networks:
      - replication_net
```

## ЧАСТЬ 3: Инструкция по запуску в один клик и проверке результата

### Шаг 1. Жесткий перезапуск Docker с полной очисткой кэша
Откройте терминал вашего сервера `nt1` в папке проекта и выполните команду:
```bash
docker compose down -v && docker compose up -d
```
*   **Что происходит:** Флаг `-v` (volumes) на корню уничтожает все старые скрытые заблокированные диски Docker, которые хранили прошлые ошибки авторизации и пустые таблицы. Контейнеры поднимаются абсолютно чистыми.
*   ⚠️ **Важно:** После выполнения этой команды убирайте руки от клавиатуры и **ждите ровно 1 минуту**. Контейнеры должны успеть запуститься, прочитать файлы из папки `init`, создать пользователей и связаться между собой по внутренней сети.
